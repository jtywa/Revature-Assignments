1. **Tell me about a time you had a disagreement with a team member about a project decision.**
	In my final year of college, I worked on a senior design product with a team of other students. The project was a hiking tool, a digital compass and path-tracer powered by a microcontroller and LCD screen. One member and I wanted to use a push-button rotary encoder, which was the original plan. Another member of the team wanted to handle user input through a touch screen interface, because there was an existing library for touch screen features where the rotary encoder input would have to be created from scratch, which he saw as too much work. I explained the benefits of the encoder (more compass-like user experience, easier to use with gloves, less likely to make erroneous inputs) and volunteered to own the development of the input handling software. This changed the other team member's mind so we were able to resolve the disagreement and continue on with the original plan.
	
2. **Tell me about a time you had to explain a technical concept to a non-technical stakeholder.**
	I created and manage a portfolio and booking website for a photographer business in Fort Worth. When creating the site, I asked the client for all photo and video they would like to appear in the showcase gallery. The client sent very large and uncompressed files to me and I informed them that I would be compressing them to be optimized for web. The client was upset at first, because they wanted customers to see the photos at their highest quality. I explained to the client that in order for users to have a good experience, images and video must load quickly. I showed him the difference between the load time and quality of raw images files  vs. their optimized webp counterparts on-screen so he could see that the images still looked good and quality loss was minimal, while loading was much faster. This helped the client understand the business value of the decision and they were happy with the idea.

3. **Tell me about a time you had to overcome a technical challenge.**
	One of my personal projects is a pair of handheld devices with buttons and a display that allow two users to play the board game Go wirelessly. The devices must be very compact, and the space needed for the microcontroller, display board, battery, switch and buttons to connect everything was too disorganized and took up too much space. I created two custom PCBs, one for the buttons and one for the microcontroller, switch and battery, and the other for the buttons. This drastically reduced the size and complexity of assembly of the devices, allowing them to meet the original size requirements and be assembled easily.
	
4. **Tell me about one of your personal projects.**
	One of my personal projects was a fullstack, online multiplayer chess client. I created the project with React for the front end, and Nodejs/Express for the back end. Users can create rooms, stored as instances on the server, and receive a 5-digit code they can share with a friend, allowing them to join that room instance. Users in the same room exchange data through a web socket, which is created and managed by the server. All inputs go through server-side move validation, powered by the open source library chess.js, and only valid moves are accepted. Game state is stored on the server, and when a valid move is received, the server communicates this change to both clients so they can update their UI. Users can also optionally create an account by providing an email and receiving a magic link, which allows them to record and view their match history.
	
5. **Tell me about a time you had to adapt to changes in project requirements after starting.**
	For the compass project I mentioned earlier, one of the key requirements originally was that the device would calculate position using only an IMU (accelerometer, gyroscope, magnetometer) without relying on GPS. As development went on, it became more and more apparent how unreliable and prone to drift this kind of setup is. The team was stubborn to change because they wanted to maintain the original vision for the system. Eventually, I was able to convince the team that in order to get usable results, we would need to switch to a system which also had access to GPS positioning. In order to compromise with the team, I devised an algorithm to record most point data with the IMU, but periodically fix error with a GPS read. This allowed us to be close to the original vision (low power, usable in remote locations) but still have the system provide accurate positioning data.
	
6. **Tell me about a time you made a mistake and had to fix it.**
	During the first run of PCBs I created in the handheld game project I mentioned earlier, There was a mistake that prevented the devices from functioning. The application I used to create the PCBs is called KiCAD, and the software relies on "footprints", the mapping of solder locations for a device, in my case the esp-32 microcontroller, to generate the soldering points on the board automatically which match that device. There is a popular online resource to download footprints for almost any device. I downloaded the footprint for the ESP-32 and imported it in the project. Everything looked fine at a glance, but after receiving the boards and testing them, I realized the creator of the footprint put the battery points in the wrong spot, which caused the software to generate a faulty PCB that did not route power to the board correctly. To fix this, I had to learn how to manually edit a footprint to correct the layout, and produce a new run of PCBs. This fixed the issue and the devices worked perfectly.
	
7. **Tell me about a time you had to take the lead in a project.**
	In the compass project, one of our members took ownership of the low level task scheduling for the microcontroller. Another member who was also inexperienced with embedded systems worked on the graphical interface of the device. Both of these members were inexperienced with embedded system design. These two members coordinated together and within a few weeks a basic system was set up. The problem was that the performance was terrible. The graphics lagged considerably and the RAM would quickly overload and crash or freeze the device. They let me know they were stuck and couldn't figure out what was causing the issue After reviewing the implementation details I saw areas for improvement that the members weren't aware of. Loops for sensor polling and display refresh were happening with no delay, as fast as the microcontroller would allow. I showed them how to create reasonable and desynced cycle times for each system in FreeRTOS, which drastically reduced lag and RAM utilization. I also showed them how to split the architecture across the two cores of the ESP-32, dividing graphics drawing and business logic, which improved performance even more.
	
8. **Tell me about a time you had to meet a tight deadline.**
	For another project in college, my team and I decided to create a mobile app that would give students directions to individual rooms on campus, as opposed to existing systems which could only locate entire buildings. A challenge we faced was that we needed data about the shape and location of each room, as well as the layout of the corridors, stairwells and hallways of each building in order to provide navigation. This data is only available from the fire escape map PDFs for each building. Manually transcribing this data for several dozen buildings would take an extremely long time, so I used generative AI to quickly create a python desktop app that used OpenCV to parse room and building numbers from each PDF, and store the perimeter and center of each room as point data associated with that room number, as well as locations of stairwells and elevators, all stored in a JSON file. This data was then easily incorporable to our project to draw routes to rooms. This allowed us to meet the tight deadline by avoiding manually transcribing hundreds of PDFs.
	
9. **Tell me about a time you had to decide between a quick fix or a long term, elegant solution.**
	In my final assignment for Game Development, one of the requirements of the project was that the game should have quests. The easiest and fastest surface-level way to implement this would be to manually give each trigger object, such as items, NPCs, enemies or locations the ability to tell the player they started or finished a quest. Instead I opted to create a global quest system that provided an interface for quest trigger objects. This extensibility made it easy to create quest triggers, and provided a single source for the data so it could persist in a quest log and trigger changes in the world or dialogue based on the progress of the player, making the game feel much more finished and full-featured.
	
10. **Tell me about a time you found a bug in production, and how you fixed it.**
	During testing of the room-finder app I mentioned earlier, we found that, for a few rooms, the positioning data was incorrect and users were not being guided to the correct location. All of the business logic seemed sound and there weren't any readily apparent issues with the UI logic either. After thinking on it for a while, I decided to look into the archive we retrieved the floorplan PDFs from for the specific building that was giving us an issue. The problem was that the floorplans PDFS for that building were rotated 90 degrees because of the shape of the building, so all points were being created with that same transformation. I updated the computer vision application so that it could detect rotation in the PDFs and adjust points accordingly. This fixed the issue, and after regenerating the JSON point data file, instructions were correct.
